## 1. What Is Fin-Eye?

Fin-Eye is a **market intelligence platform** — not a trading platform, not a broker integration. Its core promise is:

> *"Understand the forces behind price movements."*

It synthesises four independent data streams into a single **Global Alignment Score (GAS)** (0–100) and a "Market Weather" label:

| GAS Range | Label | Meaning |
|---|---|---|
| 75–100 | Mild Support | All layers broadly bullish |
| 55–74 | Mixed Signals | Disagreement between layers |
| 35–54 | Headwind | Mostly bearish conditions |
| 0–34 | High Instability | All layers aligned bearish |

### The Four Layers

```
Technical Layer (40% weight)
 └─ XGBoost + Logistic Regression + Prophet models per timeframe (1h/4h/1d/1w/1m)
 └─ Winner chosen by Sharpe Ratio on walk-forward validation
 └─ Consensus across 5 timeframes → Technical Confidence Score (0–100)

Sentiment Layer (30% weight)
 └─ Finnhub News API → FinBERT NLP sentiment scoring
 └─ Reddit (PRAW) mention volume + polarity
 └─ 30-day rolling average → Sentiment Score (0–100)

Macro Layer (30% weight)
 └─ FRED API: Fed Funds Rate, CPI, Unemployment, Yield Spread
 └─ VIX from Yahoo Finance
 └─ Composite Macro Score (0–100), market-wide (not per-symbol)

Volatility Regime
 └─ VIX classification: Low (<15) / Medium (15–25) / High (>25)
 └─ Informs Regime label: Risk-On / Transitional / Risk-Off
```

## 4. Advantages

### Product Advantages
- **Clear educational positioning** — Not "AI predicts price", but "understand regime". This is legally safe and intellectually honest.
- **Conflict Detector** is a differentiator. Most tools show signals; Fin-Eye shows when signals *disagree*, which is where the educational value is highest.
- **Multi-timeframe ML consensus** (5 timeframes, 3 competing models, Sharpe-ratio selection) is a robust, non-cherry-picked approach.
- **GAS is composable** — technical + sentiment + macro means one number captures multi-dimensional market state.
- **Three-tier cache** (Redis → DB snapshot → live compute) means the dashboard is fast even at cold start.
- **GDPR-first design** — GDPR & Legal endpoints, double opt-in, data subject rights. Important for EU launch.
- **Onboarding email sequences** (Day 3, Day 7, weekly digest) are already implemented — retention tooling is in place.
- **A/B experiment framework** is built-in — you can measure feature impact from day one.
- **Public API tier** with API key auth is already wired — monetisation of developer/institutional tier is ready.
- **Walk-forward validation** (not simple train/test split) is the right way to backtest; it's already in the ML pipeline.

### Technical Advantages
- FastAPI + asyncpg gives very high throughput for an ML-backed service.
- APScheduler runs all pipelines (OHLCV, macro, news, GAS, alerts, backups, emails) from a single process — simple to operate for MVP.
- Redis LRU eviction (`allkeys-lru`, 256MB max) is correctly configured for a cache that must degrade gracefully.
- Docker Compose setup is clean and production-like (healthchecks, named networks, persistence volumes).

## 5. Disadvantages / Risks

### Technical Risks
1. **No production Dockerfile** — the repo has `docker-compose.yml` but no `Dockerfile` for the backend or frontend. You cannot deploy to AWS ECS/EKS without this.
2. **FinBERT runs synchronously in ML pipeline** — HuggingFace Transformers inference is CPU/GPU-bound and not async. Under concurrent load this will block the event loop if not properly offloaded to a thread pool or separate worker.
3. **Yahoo Finance (yfinance) is unofficial** — no SLA, breaks regularly on API changes, rate-limited at scale. Fine for MVP, a liability in production.
4. **APScheduler single-process** — all 10 scheduled jobs run in one process. If the process crashes, all pipelines stop. No job persistence means missed jobs are lost on restart (no `misfire` replay beyond grace_time).
5. **ML model artifacts stored locally** (`data/models/`) — not in S3 or any shared store. If the server is reprovisioned, models are lost and must be retrained.
6. **No ML model versioning** — `model_registry.jsonl` is a flat file. No MLflow, no model lineage. Hard to roll back a bad model.
7. **Redis has no authentication** in docker-compose — fine for local dev, a security issue in production.
8. **`max_connections=100` on PostgreSQL** — with async SQLAlchemy pool + APScheduler, this can be exhausted under load.
9. **No rate limiting on API endpoints** — the PRD mentions Kong/API Gateway but it is not in the codebase. All public endpoints are unprotected from brute force / DDoS.
10. **LSTM model noted in PRD but not in ml_pipeline.py** — the implemented models are XGBoost, Logistic Regression, and Prophet. The LSTM (highest accuracy potential) is documented but not yet built.

### Business Risks
1. **MiFID II / regulatory exposure** — even with disclaimers, if a user claims they traded on a GAS signal and lost money, you are exposed. Legal review is not optional.
2. **Model accuracy dependency** — if forward Sharpe ratio drops below 50% of backtest (expected), users will churn. The model drift detection is built but not yet proven in production.
3. **Free tier is very generous** — if the free tier is too useful, paid conversion will be poor. The current free/paid split (delayed vs real-time macro) is reasonable but untested.
4. **Content dependency** — 2 blog posts/week is a significant ongoing commitment for a solo founder / small team.

## 9. Optimised Architecture Recommendations

### For MVP (Now → 100 users)
```
[Vercel] → [EC2 t3.large: FastAPI + APScheduler]
                ↓
         [RDS db.t3.small]  [ElastiCache t3.micro]
                ↓
         [S3: model artifacts, backups]
```
- Add a production `Dockerfile` immediately.
- Use `gunicorn -k uvicorn.workers.UvicornWorker` (4 workers) instead of plain `uvicorn` for process resilience.
- Enable Redis AUTH password in production.
- Set `max_connections=200` in PostgreSQL config.

### For Growth (100–1,000 users)
- Move FinBERT inference to a **separate Celery worker** (don't block FastAPI event loop).
- Use **S3 for model artifacts** instead of local filesystem.
- Add **CloudWatch alarms** on DB CPU > 80%, Redis memory > 70%.
- Add **rate limiting** via AWS API Gateway or nginx `limit_req_zone`.

### For Scale (1,000+ users)
- Migrate to **ECS Fargate** for zero-downtime deploys.
- Add **RDS read replica** for analytics/backtesting queries.
- Use **Redis cluster** with replication for HA.
- Consider **TimescaleDB** extension on RDS for time-series compression (can reduce OHLCV storage by 90%).
- Run ML training jobs on **AWS SageMaker** or spot GPU instances.

### Always
- Store secrets in **AWS Secrets Manager** or Parameter Store (not `.env` files).
- Enable **AWS WAF** once you have paying users (protect against scraping).
- Set up **Sentry** for error tracking before launch.
- Use **Reserved Instances** (1-year) once you're confident in server sizes — saves 40%.
