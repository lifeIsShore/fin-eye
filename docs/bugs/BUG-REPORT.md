## BUG-001 — Redis Has No Password in Production Config 🔴 CRITICAL

**File:** `docker-compose.yml`, `backend/.env.example`

**Description:**
The Redis service in `docker-compose.yml` has no `requirepass` configuration. If the same compose file or Redis config is used in any non-local environment (staging, prod), Redis is exposed without authentication. An attacker who can reach the Redis port can read all cached GAS scores, session tokens, macro data, and potentially write arbitrary cache entries to corrupt API responses.

**Reproduction:**
```bash
redis-cli -h <server-ip> -p 6379
ping  # Returns PONG with no auth
keys *  # Dumps all cached keys
```

**Impact:**
- Cache poisoning: Attacker injects false GAS scores
- Session token theft if JWT tokens are cached
- Full cache dump of all user-facing data

**Fix:**
```yaml
# docker-compose.yml
redis:
  command: redis-server --appendonly yes --maxmemory 256mb --maxmemory-policy allkeys-lru --requirepass "${REDIS_PASSWORD}"
```
```python
# backend/app/db/redis_client.py — ensure password is passed
redis_url = f"redis://:{settings.redis_password}@{settings.redis_host}:{settings.redis_port}/0"
```
Add `REDIS_PASSWORD` to `.env.example` and rotate it as a secret (AWS Secrets Manager in prod).

## BUG-003 — ML Model Artifacts Stored on Local Filesystem 🔴 CRITICAL

**File:** `backend/app/services/ml_pipeline.py` line ~19

```python
ARTIFACT_DIR = os.path.join(os.path.dirname(__file__), "..", "..", "data", "models")
REGISTRY_FILE = os.path.join(ARTIFACT_DIR, "model_registry.jsonl")
```

**Description:**
All trained ML models are written to a local directory (`backend/data/models/`). In any containerised or cloud deployment, this directory is ephemeral. A server restart, container recreation, or EC2 instance replacement will destroy all trained models. When models are gone, `technical_service.compute_technical_consensus()` will fall back to the default score of `50.0` for every symbol, making all GAS scores equal to `50 × 0.4 + sentiment × 0.3 + macro × 0.3`. The dashboard shows data, but the technical layer is completely wrong — silently.

**Impact:**
- Silent data corruption (users see wrong GAS, no error shown)
- All technical layer scores become 50.0 (neutral) after deploy
- No recovery without retraining (5+ years of data, hours of compute)

**Fix:**
1. After training, upload model artifacts to S3:
```python
import boto3
s3 = boto3.client("s3")
s3.upload_file(local_model_path, settings.s3_bucket, f"models/{symbol}/{model_name}.joblib")
```
2. On inference, download from S3 if not cached locally:
```python
if not os.path.exists(local_path):
    s3.download_file(settings.s3_bucket, s3_key, local_path)
```
3. Add `MODEL_REGISTRY_S3_BUCKET` to config and `.env.example`.

## BUG-004 — FinBERT / Transformers Inference Blocks the AsyncIO Event Loop 🔴 CRITICAL

**File:** `backend/app/services/gas_precompute.py`, `technical_service.py`, `sentiment_service.py`

**Description:**
`compute_technical_consensus(symbol)` is called inside `asynccontextmanager`-based FastAPI endpoints and the APScheduler async event loop. The function runs scikit-learn / joblib inference synchronously. `run_in_executor` is used in `gas_precompute.py` for the technical service — **but this is not consistently applied across all call sites.** If `technical_service` or `sentiment_service` is called directly from an async route handler without `run_in_executor`, the entire FastAPI event loop is blocked for the duration of inference (~100ms–2s per symbol).

**Impact:**
- Under concurrent load (10+ users simultaneously), all API responses become slow
- Scheduler jobs can starve API requests
- P95 latency spikes above the 500ms SLA target

**Fix — Ensure all CPU-bound calls use run_in_executor:**
```python
# In any async context that calls CPU-bound inference:
import asyncio

loop = asyncio.get_running_loop()
result = await loop.run_in_executor(
    None,  # Use default ThreadPoolExecutor
    compute_technical_consensus,
    symbol
)
```
**Long-term fix:** Separate the ML worker into its own process using Celery + Redis as the broker. FastAPI only reads cached results.

## BUG-007 — APScheduler Has No Job Persistence; Missed Jobs Are Lost 🟠 HIGH

**File:** `backend/app/services/scheduler.py`

**Description:**
`AsyncIOScheduler` is initialised without a `jobstore`. All job state is in-memory. If the backend process crashes or restarts, any job that was scheduled but not yet executed is simply dropped — it will not run until the next scheduled time. For a daily backup job or macro fetch job, a restart during the scheduled window means that day's job never runs.

**Impact:**
- Daily OHLCV data gap if server restarts at 18:05 UTC
- Daily DB backup silently skipped
- Macro scores become stale without alerting anyone

**Fix — Add SQLAlchemy job store for persistence:**
```python
from apscheduler.jobstores.sqlalchemy import SQLAlchemyJobStore

jobstores = {
    'default': SQLAlchemyJobStore(url=settings.database_url)
}
scheduler = AsyncIOScheduler(jobstores=jobstores, timezone="UTC")
```
This persists job run history to PostgreSQL and replays missed jobs within `misfire_grace_time`.

## BUG-008 — PostgreSQL max_connections=100 Will Be Exhausted Under Load 🟠 HIGH

**File:** `docker-compose.yml` line ~32

```yaml
command: >
  postgres
    -c max_connections=100
```

**Description:**
SQLAlchemy async engine typically uses a pool of 5–20 connections per worker. With 4 Uvicorn workers + APScheduler (creating its own sessions per job), plus pgAdmin, the pool can easily hit 100 connections. At 100 connections, new connection attempts get `FATAL: sorry, too many clients already` — causing 500 errors for all users.

**Impact:**
- Hard service outage when connection limit is reached
- Error is not graceful — users see 500 Internal Server Error
- Occurs at moderate load (~50 concurrent users)

**Fix:**
1. Increase `max_connections=200` in postgres config
2. Add PgBouncer as a connection pooler in front of PostgreSQL:
```yaml
pgbouncer:
  image: pgbouncer/pgbouncer
  environment:
    DATABASES_HOST: db
    DATABASES_PORT: 5432
    DATABASES_DBNAME: fin_eye
    PGBOUNCER_POOL_MODE: transaction
    PGBOUNCER_MAX_CLIENT_CONN: 500
    PGBOUNCER_DEFAULT_POOL_SIZE: 25
```
3. Set SQLAlchemy pool size explicitly:
```python
engine = create_async_engine(url, pool_size=10, max_overflow=5, pool_timeout=30)
```

## BUG-010 — Model Registry Is a Flat `.jsonl` File; No Rollback Possible 🟡 MEDIUM

**File:** `backend/app/services/ml_pipeline.py`

```python
REGISTRY_FILE = os.path.join(ARTIFACT_DIR, "model_registry.jsonl")
```

**Description:**
The model registry is a local `.jsonl` (JSON Lines) file. There is no versioning, no ability to roll back to a previous model, and no atomic update. If a newly trained model is corrupt or worse-performing, there is no mechanism to revert. Additionally, the registry file is in the ephemeral local filesystem (see BUG-003).

**Impact:**
- A bad monthly retrain poisons all predictions with no recovery path
- Concurrent writes to the JSONL file from multiple workers could corrupt it
- No audit trail of model performance over time

**Fix:**
Add a `model_versions` table to PostgreSQL:
```sql
CREATE TABLE model_versions (
    id SERIAL PRIMARY KEY,
    symbol VARCHAR(20) NOT NULL,
    timeframe VARCHAR(10) NOT NULL,
    model_type VARCHAR(50) NOT NULL,
    s3_key TEXT NOT NULL,
    sharpe_ratio FLOAT,
    accuracy FLOAT,
    trained_at TIMESTAMPTZ DEFAULT NOW(),
    is_active BOOLEAN DEFAULT FALSE
);
```
Use a database transaction to swap `is_active` flags atomically when promoting a new model.

## BUG-012 — Sentiment Score Mapping Has Incorrect Range Assumption 🟡 MEDIUM

**File:** `backend/app/services/gas_precompute.py`

```python
score = ((float(avg_raw) + 1.0) / 2.0) * 100.0
```

**Description:**
This formula assumes `sentiment_score` is in `[-1, +1]`. However, `vaderSentiment` returns a compound score in `[-1, +1]`, while FinBERT returns a probability distribution across [negative, neutral, positive] classes, typically stored as one value per article in range `[0, 1]`. If `SentimentAggregate.sentiment_score` is stored as a 0–1 FinBERT probability (not a -1 to +1 compound score), the formula gives wrong results:
- A perfectly positive article (score=1.0) → `(1.0 + 1.0) / 2 × 100 = 100` ✅
- A perfectly negative article (score=0.0) → `(0.0 + 1.0) / 2 × 100 = 50` ❌ (should be 0)

This means negative sentiment is systematically misrepresented as neutral.

**Fix:**
Determine the actual range of `sentiment_score` stored in `SentimentAggregate`:
```python
# If stored as 0–1 (FinBERT probability of positive):
score = float(avg_raw) * 100.0

# If stored as -1 to +1 (VADER compound):
score = ((float(avg_raw) + 1.0) / 2.0) * 100.0
```
Add a data contract comment to the `SentimentAggregate` model making the expected range explicit.

## BUG-014 — GAS Cache Warm on Startup Can Cause Slow Cold Start 🟢 LOW

**File:** `backend/app/main.py`

```python
async with AsyncSessionLocal() as session:
    summary = await run_gas_precompute_batch(session)
```

**Description:**
On startup, the app runs `run_gas_precompute_batch` for all default symbols **synchronously in the lifespan context**. If FinBERT inference or FRED lookups are slow (cold start, model loading), this can take 30–120 seconds. During this time, the ASGI server is alive but all ML work is blocking. If behind a load balancer with a 30-second health check timeout, the app will fail its first health check and be killed before it serves any traffic.

**Impact:**
- Deployment failures behind ALB/ELB/ECS
- Slow restarts in development (annoying)

**Fix:**
Move the GAS warm to a background task that runs **after** the server is ready:
```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # ... init DB, Redis, scheduler ...
    
    # Start GAS warm as a non-blocking background task
    asyncio.create_task(_warm_gas_cache())
    
    yield
    # ... shutdown ...

async def _warm_gas_cache():
    await asyncio.sleep(5)  # Let health checks pass first
    async with AsyncSessionLocal() as session:
        await run_gas_precompute_batch(session)
```

## BUG-015 — No Global Exception Handler; Unhandled Errors Return Raw Stack Traces 🟠 HIGH

**File:** `backend/app/main.py`

**Description:**
FastAPI's default unhandled exception response includes the exception class name and sometimes a partial stack trace in the 500 response body. In production, this exposes internal architecture details (file paths, library versions, SQL queries in some ORM errors).

**Impact:**
- Information disclosure to attackers
- Poor user experience (raw JSON error vs friendly message)

**Fix:**
```python
from fastapi import Request
from fastapi.responses import JSONResponse

@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    logger.exception("Unhandled exception on %s %s", request.method, request.url)
    return JSONResponse(
        status_code=500,
        content={"detail": "An internal error occurred. Please try again later."}
    )
```

## BUG-016 — No CSRF Protection on State-Changing Endpoints 🟠 HIGH

**File:** `backend/app/main.py`, all POST/PUT/DELETE endpoints

**Description:**
The API uses JWT Bearer tokens in `Authorization` headers, which are CSRF-safe by design. However, if any endpoint also accepts cookies for authentication (e.g., session cookies in future), CSRF protection is required. More immediately, the CORS config uses `allow_credentials=True` — if the origin whitelist is too broad or `*` is used in any environment, credential-carrying cross-origin requests are permitted.

**Fix:**
1. Verify `settings.allowed_origins` is a strict list (never `["*"]` with `allow_credentials=True`).
2. If cookie-based auth is ever added, add `starlette-csrf` middleware.
3. Add a check in CI to fail if `allow_origins=["*"]` and `allow_credentials=True` are combined.

## BUG-018 — Backtesting Service Has No Input Validation on Date Ranges 🟡 MEDIUM

**File:** `backend/app/services/backtesting_service.py` (inferred from router)

**Description:**
The backtesting endpoint accepts date range parameters. Without server-side validation, users can request:
- Date ranges spanning 20+ years (exhausts memory loading all OHLCV data)
- Future dates (returns empty results with no error)
- `start_date > end_date` (causes pandas/SQL errors that leak to the client)
- Extremely short ranges (< 50 bars, below the ML feature engineering minimum)

**Impact:**
- Out-of-memory crashes for large date ranges
- Confusing empty results for future dates
- 500 errors from pandas/SQLAlchemy for invalid date orders

**Fix:**
```python
from pydantic import validator

class BacktestRequest(BaseModel):
    symbol: str
    start_date: date
    end_date: date
    strategy: str
    
    @validator('end_date')
    def end_after_start(cls, v, values):
        if 'start_date' in values and v <= values['start_date']:
            raise ValueError('end_date must be after start_date')
        return v
    
    @validator('start_date')
    def min_history(cls, v):
        if (date.today() - v).days < 365:
            raise ValueError('Minimum 1 year of history required')
        return v
    
    @validator('end_date')
    def not_future(cls, v):
        if v > date.today():
            raise ValueError('end_date cannot be in the future')
        return v
```
